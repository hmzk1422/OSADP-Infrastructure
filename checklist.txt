# 7. Copy-paste production acceptance checklist

Below is the version I would put in a repository as `PRODUCTION_READINESS.md`. It is intentionally implementation-oriented: each item should become a test, an automated assertion, or a documented operational verification.

Rule: `[x]` means evidence exists and the test passes. It does not mean the feature was merely implemented. Any critical test that has not been executed is `[ ]`.

The checks below are designed to exclude strategy expectancy and returns. Because the attached code appears to include a Rust-based Binance execution/data pipeline, I have included specific market-data, order-management, and persistence checks relevant to that architecture.

## 0. Process startup and configuration

```
[ ] Application refuses to start if a required configuration value is missing.
[ ] Application refuses to start if a numeric configuration value is NaN, infinite, or outside its allowed range.
[ ] Application refuses to start if a required risk limit is zero, negative, or unintentionally unlimited.
[ ] Application validates all instrument symbols against the configured venue before trading.
[ ] Application validates tick size, quantity step, minimum quantity, and minimum notional before enabling an instrument.
[ ] Application validates that configured order types and time-in-force values are supported by the selected venue.
[ ] Application validates that strategy, feature engine, risk engine, and execution adapter versions are compatible.
[ ] Application refuses to start when its persistent state schema is incompatible with the running binary.
[ ] Application refuses to start if its persistent state cannot be read or verified.
[ ] Application does not silently create an empty account state when a previously existing state file is missing.
[ ] Application distinguishes a first-ever initialization from an unexpected loss of existing state.
[ ] Application validates that the selected environment is explicitly production, testnet, or simulation.
[ ] Application requires an explicit production-mode configuration rather than inferring production from missing test settings.
[ ] Application verifies the exchange endpoint, account identity, and permitted trading environment before enabling live orders.
[ ] Application verifies that API credentials are present and valid before enabling authenticated operations.
[ ] Application refuses to start if credentials have unintended withdrawal permissions, where those permissions can be checked.
[ ] Application verifies required filesystem paths, permissions, available disk space, and writable log/state directories.
[ ] Application verifies database connectivity and schema compatibility before enabling components that depend on them.
[ ] Application validates all timeout, retry, queue-capacity, and retention settings.
[ ] Application refuses configurations where retry intervals, deadlines, or resource limits contradict each other.
[ ] Application logs the effective non-secret configuration and a configuration hash at startup.
[ ] Application never logs API secrets, authentication headers, or full signed request URLs.
[ ] Application starts in a non-trading state until all mandatory startup checks pass.
[ ] Application does not submit an order during module initialization or before startup validation completes.
[ ] Application exits with a nonzero status when a mandatory startup check fails.
```

[ ] Any fallback transport preserves message framing, authentication, ordering requirements, and reconnect semantics.
[ ] The fallback transport has its own bounded queues and resource limits.
[ ] A transport change cannot silently duplicate or omit execution commands.
[ ] The system records the reason, time, and actions taken when entering degraded mode.
[ ] The system does not repeatedly oscillate between normal and degraded modes around one threshold.

# 20. How I would actually deem it production-grade

I would use three approval states, rather than a single percentage-complete score.

NO-GO — Unsafe

Any unexplained position discrepancy, risk-limit bypass, duplicate-order path, unbounded critical queue, unresolved crash-recovery defect, or failed mandatory test blocks live deployment.

CONDITIONAL — Shadow or testnet only

Core functionality works, but fault injection, recovery, performance limits, operational controls, or live-environment validation remain incomplete.

GO — Approved for controlled production

All critical tests pass, failure behavior is demonstrated, the release is reproducible, operational controls work, and initial exposure is explicitly limited.

One final point: no checklist can prove that a trading system will run correctly 100% of the time. You can, however, require evidence that specified failure modes have been tested, critical invariants are enforced, uncertainty is handled explicitly, and the system fails in a controlled manner when assumptions break.

The goal is not to prove that nothing can fail. It is to ensure that failures are detected, contained, recoverable, and never silently converted into unintended trading exposure.

If I had to prioritize just five areas before deploying any meaningful capital, they would be:

1. Order submission ambiguity and duplicate prevention.
2. Position and order reconciliation after crashes and reconnects.
3. Independent risk enforcement under concurrency and failure.
4. Market-data validity and order-book recovery.
5. Memory/queue exhaustion, kill-switch behavior, and safe restart.

Those five deserve considerably more scrutiny than whether the process stays alive for a month.
