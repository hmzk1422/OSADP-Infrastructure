# UETS Trading System — Implementation Specification

## Global Requirements

1. Implement the system in **Rust**.
2. Follow the existing repository structure and conventions. Inspect the current code before modifying anything.
3. Do not rewrite unrelated components or introduce unnecessary abstractions.
4. Keep the strategy engine (`uets`) independent of exchange-specific execution logic.
5. All trading modes must use the same core trading interface and shared calculation logic.
6. Prioritize low latency, low memory usage, predictable behavior, and correctness.
7. Do not add shell commands or a CLI to `uets_trades`. It must be a Rust library.
8. Do not silently discard errors, order events, database writes, or important trading records.
9. Implement in phases. Compile and test each phase before proceeding.
10. Do not claim functionality is implemented unless it exists and has been tested.

---

# Phase 1: Trading and Execution — `uets_trades`

## 1.1 Responsibilities

Create or update the Rust library at `components/pipelines/uets_trades/`.

Structure:

```text
components/pipelines/uets_trades/
├── live_test/
├── live_trade/
├── playback/
└── calc/
```

- `live_test/`: paper trading using live market data.
- `live_trade/`: real trading using live market data and broker/exchange execution.
- `playback/`: offline backtesting using historical or synthetic data, with accelerated event replay.
- `calc/`: shared PnL, equity, capital, risk and performance calculations.

Keep the library modular. Follow existing project conventions for module declarations and public interfaces.

## 1.2 Execution ownership

The exchange execution interface must reside in `components/pipelines/uets_manager`, not inside `uets`.

The execution flow must be:

```text
Exchange market data
        ↓
UETS computes features and strategy decision
        ↓
Trade intent (long, short, exit, etc.)
        ↓
uets_manager validates and routes the intent
        ↓
Selected execution backend
        ├── live_test: simulated execution
        ├── live_trade: real broker/exchange execution
        └── playback: simulated execution against replayed events
        ↓
Execution events and portfolio updates
        ↓
uets_trades/calc
```

The strategy must not submit orders directly to the exchange WebSocket or broker API.

The strategy should use a consistent interface for actions such as `long()`, `short()` and `exit()`. The selected execution backend determines how these actions are handled. Do not implement mode switching by unsafely replacing functions at runtime; use explicit backend selection or dependency injection.

A trade intent is not a confirmed fill. Model order lifecycle states, including submitted, accepted, partially filled, filled, rejected and cancelled where applicable.

## 1.3 Trading modes

### A. `live_test`

- Consume live exchange market data.
- Never submit real orders.
- Simulate capital, order acceptance, fills, fees and positions.
- Use configurable execution assumptions, including spread and slippage.
- Apply the same portfolio and reporting calculations used by the other modes.

### B. `live_trade`

- Consume live exchange market data.
- Route orders through `uets_manager` to the configured broker or exchange.
- Track actual acknowledgements, fills, partial fills, rejections, cancellations, fees and positions.
- Maintain appropriate safeguards against duplicate orders, stale data and uncertain execution state.
- Never silently fall back to paper execution or switch into live mode without explicit configuration.

### C. `playback`

- Replay historical or synthetic market data through a deterministic event loop.
- Support configurable accelerated playback, including targets such as 10× and 100× where computationally feasible.
- Preserve event ordering and strategy timing semantics.
- Simulate execution without submitting real orders.
- Allow reproducible backtests using fixed input data, configuration and random seeds where randomness is involved.
- Do not artificially skip required events merely to achieve a speed target.

## 1.4 OFMR triple-barrier handling — mandatory

OFMR uses the triple-barrier method. Inspect its existing strategy implementation to determine exactly how its barriers are defined and whether they are used for live exits, training labels, or both. Do not assume these uses are interchangeable.

Where triple barriers govern live trade exits, support:

- Entry price and entry timestamp.
- Profit-taking barrier (TP).
- Stop-loss barrier (SL).
- Vertical barrier / maximum holding time.
- Barrier parameters and the values used to calculate the actual barrier prices.
- Exit timestamp, exit price and exit reason.
- Fees, slippage and realized PnL.

Enforce the configured barriers in every applicable execution mode. Use native broker/exchange protective orders where supported and appropriate. Otherwise, implement exit monitoring with explicit safeguards for disconnects, partial fills and stale market data.

Do not invent OFMR's TP/SL values or change its existing strategy rules without inspecting the source and obtaining clear justification.

## 1.5 Shared calculations — `calc/`

Implement one shared calculation layer used by all three modes.

It must calculate, where applicable:

- Initial and allocated capital.
- Current cash, equity and available capital.
- Realized and unrealized PnL.
- Fees and trading costs.
- Return and cumulative return.
- Drawdown and maximum drawdown.
- Sortino ratio and other existing performance metrics.
- Position and exposure information.
- Trade counts, win rate and other existing report statistics.

Define each metric precisely and use consistent formulas across modes. Do not calculate the same metric differently in paper, live and playback.

Use the latest available valid data. Maintain live state incrementally instead of recomputing the entire trade history on every update.

Use a configurable, nominal 100 ms reporting cadence where appropriate. A report update must not block strategy execution or order routing.

# Phase 2: Persistence — `components/pipelines/uets_db`

## 2.1 Responsibilities

Create a Rust database component at:

```text
components/pipelines/uets_db/
```

This component owns:

- RocksDB initialization and configuration.
- Database lifecycle and shutdown.
- Record schemas and serialization.
- CRUD operations.
- Indexed queries.
- Batched writes.
- Session management.
- Schema versioning.
- Recovery, integrity checks and error handling.

Other components must not open or manipulate RocksDB directly. They must use the `uets_db` API.

Optimize for low memory overhead and low write latency. Do not create a separate RocksDB instance for every strategy.

## 2.2 Logical database structure

Maintain two logical data domains:

```text
live_db/
├── trades/
└── portfolio/
```

These are logical domains, not a requirement to create separate physical database instances.

### A. `trades`

Store the information required to understand what the strategy observed, decided and executed.

Include, where applicable:

- Session ID.
- Strategy ID.
- Asset/ticker.
- Event timestamp.
- The feature values and market inputs actually consumed by `compute_features`.
- Strategy decision and relevant decision metadata.
- Trade intent.
- Order lifecycle events.
- Entry and exit prices.
- TP, SL and vertical-barrier information for OFMR where applicable.
- Fill quantity, fees and realized PnL.
- Strategy/model version and configuration identifiers.

Capture the model's actual inputs at the required observation cadence, nominally 100 ms. Preserve the actual event timestamps and do not assume every exchange event arrives exactly every 100 ms.

Do not store a complete duplicate market feed for every strategy. Store the inputs needed to audit or reproduce decisions, and retain additional raw data only when required.

### B. `portfolio`

Store portfolio snapshots and calculated reporting metrics produced by `uets_trades/calc`.

Include, where applicable:

- Session ID.
- Strategy ID.
- Asset ID.
- Snapshot timestamp.
- Allocated capital.
- Cash and equity.
- Realized and unrealized PnL.
- Cumulative return.
- Sortino ratio.
- Drawdown.
- Exposure and other existing reporting metrics.

Use the strategy-instance identity convention:

```text
ofmr@btcusdt
ofmr@ethusdt
moe@btcusdt
```

Represent this identity through explicit `strategy_id` and `asset_id` fields or a stable composite identifier. Do not rely solely on parsing strings.

For trade records, store the ticker/asset separately from the strategy identity. For portfolio records, preserve both the strategy and asset identity so individual strategy instances can be queried independently.

## 2.3 Session organization

Every applicable record must include a stable `session_id`.

Sessions must support independent querying, reporting, archival and recovery. For example:

```text
session_1
session_2
session_3
```

The logical session organization must not force the creation of a separate RocksDB instance for every session. Begin with a shared RocksDB instance and session-aware keys/indexes. Use separate physical database files only if the existing architecture or measured requirements justify them.

Implement efficient retrieval by:

- Session.
- Strategy.
- Asset.
- Time range.
- Combinations of these fields.

Use compact, versioned binary serialization. Avoid JSON as the default high-volume record format unless the existing system requires it.

Use appropriate batching and atomic writes for related records and indexes. Define explicit durability and recovery requirements; do not silently lose critical order or fill events.

## 2.4 Portfolio persistence cadence

Portfolio calculations are produced by `uets_trades/calc`. Persist portfolio snapshots at a nominal 100 ms cadence while the strategy instance is active, subject to the configured sampling policy.

- If no relevant state changes, equity and PnL can remain unchanged.
- If a position is open and market prices change, unrealized PnL and equity may change.
- Do not assume portfolio growth is flat merely because no new trade was opened.
- When a strategy instance is inactive, follow its configured lifecycle and reporting policy.
- Finalize and persist a session summary when the session ends.

Use asynchronous persistence so disk I/O does not block the strategy or reporting calculation path. Apply bounded queues and explicit backpressure. Critical order/fill events must not be silently dropped if the queue fills or storage fails.

# Phase 3: Monitoring GUI — `components/pipelines/uets_gui`

## 3.1 Responsibilities

Create a Rust GUI component at:

```text
components/pipelines/uets_gui/
├── gui/
└── controls/
```

For this phase, implement the monitoring interface only. Leave strategy enable/disable and other operational controls unimplemented unless explicitly requested.

The GUI should have a keyboard-driven, Vim-inspired interface. Do not sacrifice clarity or readability merely to imitate a terminal.

## 3.2 Strategy-instance monitoring

Display instances such as:

```text
ofmr@btcusdt
ofmr@ethusdt
moe@btcusdt
```

For each instance, display relevant information, including:

- Current status.
- Allocated capital.
- Cash and current equity.
- Realized and unrealized PnL.
- Absolute and percentage return.
- Sortino ratio.
- Current and maximum drawdown.
- Open positions and exposure.
- Trade counts and win rate.
- Latest market-data and decision timestamps.
- Decision-to-order and order-to-fill latency where measurable.
- Strategy processing latency.
- Memory consumption.
- CPU usage where available.
- Persistence queue depth, write latency and storage errors.

Clearly distinguish unavailable metrics from zero-valued metrics.

## 3.3 Data flow and persistence ownership

The GUI must read reporting data from `uets_trades/calc` through a defined interface or subscription mechanism. It must not independently recalculate authoritative trading metrics.

The GUI is **not responsible for saving trading data**.

Use this flow:

```text
uets_trades/calc
        ├──→ uets_gui (display)
        └──→ uets_db (asynchronous persistence)
```

The GUI may request historical records or reports from `uets_db` for display. It must not sit between `uets_trades` and `uets_db`, and persistence must continue when the GUI is closed.

The monitoring GUI must not block market-data processing, strategy decisions, order execution or database writes.

# Phase 4: Implementation and Verification

Implement in this order:

1. Inspect the existing repository, OFMR implementation, execution pathways and reporting calculations.
2. Document the current interfaces and identify the smallest required changes.
3. Implement the shared trading interface and execution backend selection.
4. Implement or adapt `live_test`, `live_trade` and `playback`.
5. Verify OFMR's triple-barrier semantics and implement the required exit handling.
6. Implement shared `calc` metrics and the 100 ms reporting mechanism.
7. Implement `uets_db`, its schemas, indexes, session handling and asynchronous persistence.
8. Implement the GUI as a read-only monitoring consumer.
9. Integrate the components and test failure handling.
10. Benchmark latency and memory before claiming performance targets have been met.

## Required tests

- Paper mode never sends real orders.
- Live mode routes orders only through `uets_manager`.
- Playback never sends real orders.
- TP, SL and vertical-barrier behavior is correct wherever applicable.
- Partial fills, rejections, fees and cancellations update state correctly.
- Shared metrics produce consistent results across execution modes.
- Session, strategy, asset and time-range database queries return correct records.
- Restart and recovery behavior is tested.
- Database failure and persistence-queue saturation do not silently discard critical events.
- Closing the GUI does not stop trading or persistence.
- Measure memory usage with many simultaneous strategy instances.
- Measure strategy latency, execution latency, reporting latency and database-write latency under representative load.

Do not add extra infrastructure, database engines, CLI commands or features outside this specification without first explaining why they are necessary.

At completion, provide a concise report of the files changed, architecture implemented, tests executed, benchmark results, unresolved issues and any deviations from this specification.
